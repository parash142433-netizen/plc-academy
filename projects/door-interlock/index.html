Basic Door Interlock project · Schneider Zelio Logic · SR2A201BD

Build a cleanroom door interlock, step by step

In this tutorial you program a door interlock for two chains of cleanroom airlocks on a Zelio Logic smart relay, in ladder. You build the first version line by line, then improve it the way you would improve a delivered program: find what it does wrong in an emergency, change it, and prove the change. The last steps test the program, and a simulator runs both versions.

Build steps
    Understand

    Start with the rooms, not the relay

    A cleanroom suite is a set of rooms kept at different air pressures. The cleaner the room, the higher its pressure, so air always flows out towards the dirtier side. If two doors of the same room are open at once, air rushes straight through and the pressure difference that protects the product collapses. A door interlock prevents that: while one door of a room is open, the other doors of that room stay locked.

    Engineer's thinking

    Which doors must never be open together?
    Any two doors of the same room. D2 and D3 both belong to room A2, so they are interlocked. D1 and D5 both open onto the corridor, but the corridor is a general area with no pressure to protect, so they are not.
    Is "closed" enough?
    No. When a door closes, the room needs a moment for its pressure to recover. So a door counts as open for a short hold time after it closes.
    What can hurt people?
    Being trapped. In an emergency every door must release immediately, and a power failure must leave the doors unlocked. This requirement overrides all the others.
    What does the operator need to see?
    A clear message when the emergency circuit has been triggered, which stays until someone resets it.

    • A Zelio Logic SR2A201BD smart relay and its programming cable, if you want to run it for real (step 2).

    Understand

    List the I/O and choose the hardware

    Seven doors need seven "door open" signals and seven lock outputs. Add an emergency input and a reset button, and you have 9 inputs and 7 outputs. That is a job for a smart relay, not a full PLC.

    The count

    • 7 door switches, one per door (on = door open)
    • 1 emergency circuit input (on = healthy)
    • 1 reset push button
    • 7 lock outputs, one per door (on = locked)

    The hardware

    • Zelio Logic SR2A201BD: a compact smart relay with 12 digital inputs (I1–I9, IA–IC), 8 relay outputs (Q1–Q8), a 24 V DC supply, and a display with keys
    • One relay output per lock, switching the lock's 24 V DC supply
    • Spare: inputs I8, IB, IC and output Q8, for a later door or a beacon

    I/O allocation

    AddressSignalOn meansDevice
    I1–I7Door D1–D7 positionDoor openDoor position switch on each door
    I9Emergency circuitHealthy (not pressed)Normally closed emergency buttons wired in series
    IAResetPressedNormally open push button

    Robustness habits: choose what "on" means

    • Emergency input on = healthy. The buttons are normally closed and wired in series to I9. Pressing any of them opens the circuit, and so does a broken wire or a lost supply. Every failure reads as "emergency", which is the safe direction.
    • Locks energise to lock. An electromagnetic lock holds only while it has power. If the relay, the 24 V supply or the module fails, every door is free to open (R6). People can always get out; only the pressure cascade suffers.
    • Door switch on = open. This is the simplest wiring, but note its weak side: a broken wire reads as "closed". The checklist in step 13 shows how to make it fail safe as well.

    The PLC is not the only emergency release

    In a real installation the emergency circuit should also cut the lock supply directly, through a safety relay or contactor. The program's release (steps 8 and 10) is a second layer that keeps the logic correct. It is not a substitute for the hardwired one.

    Plan

    Turn the floor plan into an interlock matrix

    Before writing a single line, write down which door locks which. The rule is simple: a door is locked while any other door of either of its two rooms is open. Work it out once, as a table, and the program becomes a copy of the table.

    Engineer's thinking

    Why read the table by lock, not by door?
    Because each output needs exactly one ladder line, and that line asks "which open doors lock me?". Reading the table row by row gives you the contacts of each line: Q2 needs "D1 open OR D3 open".
    Why is D1 not locked by D5?
    They share only the corridor, and requirement R3 leaves the corridor out. A matrix makes such decisions visible, so they can be reviewed before the program is written.
    What about the end rooms?
    A4 and B3 have only one door, so D4 and D7 are only locked from one side. Only the inner doors D2, D3 and D6 have two neighbours.
    Plan

    Design the program structure

    The whole program fits on 27 ladder lines in four groups. Each group answers one question, and the signals flow down the page from inputs to outputs.

    LinesGroupThe question it answersWrites
    1–7Door-open flagsWhich doors are open, while the system is healthy?M1–M7
    8–17Interlock timersWhich doors must be locked, including the hold time?T1–T7
    18–20Emergency and messageIs the system healthy? What does the display show?ME, X2
    21–27Lock outputsWhich locks get power right now?Q1–Q7

    Zelio ladder in five minutes

    • One line, five contacts, one coil. Every line has five contact columns and a coil column. Contacts in a row are in series (AND).
    • Upper case is normally open, lower case is normally closed. ME closes when ME is on; mE closes when ME is off.
    • OR by linking lines. A vertical link from a line down to the next line joins them, so either path can power the coil below.
    • The coil letter says what the coil does. [ is a normal coil that follows the line. T before a timer (TT1) is its trigger input. TX2 shows text block X2 on the display, and RX2 removes it.
    • Auxiliary relays (M1–M9, then MA, MB, …) are internal flags. A timer's contact T1 is used like any other contact.
    SymbolTypeName in this projectOn means
    M1–M7Auxiliary relayD1–D7 OPENDoor open, and the system healthy
    MEAuxiliary relaySYSTEM HEALTHYEmergency circuit closed
    T1–T7Timer, function C (off-delay)LOCK D1–D7 HOLDDoor must be locked
    X2Text blockEMERGENCY STOPMessage on the display

    Scan order matters

    The module runs the lines from top to bottom, once per cycle. Lines 1–17 read ME before line 18 writes it, so they see the value from the previous cycle, 18 ms old. Here that is harmless. But always know where a flag is written, relative to where it is read. The simulator in step 12 reproduces this delay.

    Robustness habits

    • Name every flag after what on means. A flag that is on when the system is healthy is called SYSTEM HEALTHY, never EMERGENCY STOPPED.
    • Keep each output on its own line, written in one place only.
    • Keep the same order in every group (D1 to D7), so a missing or extra line stands out.

    Create the project and configure the module

    In Zelio Soft 2, create a new program, choose the module (SR2A201BD) and the ladder language. Then set the module options before you draw any lines: they decide how fast the program reacts and how clean the input signals are.

    SettingValueWhy
    Cycle time9 × 2 ms = 18 msEvery line runs every 18 ms. A door lock reacts well within the time it takes to push a door.
    Hardware input filteringSlow (3 ms)Door switches are mechanical and bounce. The slow filter ignores pulses shorter than 3 ms.
    Watchdog actionInactiveWhat the module does if a cycle overruns its time. With 27 short lines, that cannot happen.
    Zx keysInactiveThe front-panel arrow keys could act as push buttons. Left off, so nobody can operate the doors from the front panel.

    Engineer's thinking

    Why not the fastest cycle?
    Doors move in seconds, not milliseconds. A moderate cycle time gives a calm, predictable program, and the timers keep their resolution.
    Where do the names go?
    Into the comment of each input, output, relay and timer, before you draw. The ladder editor shows those comments under each contact, so the diagram reads like the matrix.

    Robustness habits

    • Fill in the program information (author, project name, version) on the first day. It prints on every page of the listing.
    • Comment the spare I/O as "spare", so nobody mistakes an unused input for a forgotten one.
    Build

    Lines 1–7: one flag per open door

    Turn each door switch into a flag that the rest of the program uses. The flag is on only while the door is open and the system is healthy. That way, an emergency removes every "door open" request in one place.

    Lines 1–7 · Door-open flags door switch AND system healthy → M1–M7
    1. L1–L7 Each line is the same pattern: door switch In in series with ME, driving a normal coil [ Mn. Seven identical lines are easy to check, and a mistake stands out.
    2. ME is written on line 18 further down, so these lines read its value from the previous cycle (step 4).
    Line 2, liveToggle the door and the emergency circuit. Green shows where power flows.

    Engineer's thinking

    Why not use the inputs directly in the timer lines?
    You could, but then the emergency condition would have to be repeated in every timer line. The flags also give each door one clear name, "D2 OPEN", for the next group.
    Why normal coils, not set/reset?
    A door-open flag must follow the door every cycle. A normal coil does exactly that, and it cannot stay stuck on.
    Build

    Lines 8–17: interlock timers with a hold time

    Now copy the matrix into ladder. Each lock gets an off-delay timer, triggered by the open-door flags of its neighbours. The timer's contact closes as soon as a neighbour opens, and stays closed for the hold time after the neighbour closes again. That single function gives you both R1 and R2.

    Lines 8–17 · Interlock timers neighbour open → trigger TT1–TT7 (off-delay, 2.0 s)
    1. L8 Lock D1 (timer T1) is triggered by D2 open (M2), straight from the matrix row for Q1.
    2. L9–L10 Lock D2 has two neighbours. Line 9 holds M1 and links down into line 10 beside M3: "D1 open OR D3 open" triggers T2.
    3. L11–L12 The same pattern for lock D3: M2 OR M4.
    4. L13, L14, L17 The single-neighbour locks: D4 from M3, D5 from M6, D7 from M6.
    5. L15–L16 Lock D6: M5 OR M7.
    6. T1–T7 All seven timers use function C (off-delay) with a preset of 2.0 s.
    Off-delay timer, liveOpen and close D2 and watch lock D1 hold.

    Engineer's thinking

    Why an off-delay and not an on-delay?
    The lock must engage at once, and release late. An off-delay switches on with its trigger and switches off a preset time after the trigger drops.
    How long should the hold be?
    Long enough for the room pressure to recover, short enough that people do not wait at a locked door and start propping doors open. Measure the recovery time during commissioning. 2 s suits small airlocks.
    What if the door opens again during the hold?
    The trigger comes back, the timer restarts, and the lock simply stays on.
    Build

    Lines 21–27: drive the locks

    Each timer contact drives its lock output. The healthy flag goes in series on every output line, so the emergency acts on the last thing before the hardware: the moment ME drops, every lock loses power in the same cycle.

    Lines 21–27 · Lock outputs timer AND system healthy → Q1–Q7
    1. L21–L27 Tn in series with ME drives the normal coil [ Qn. These lines read ME after line 18 has written it, so the release happens in the same cycle as the emergency.
    2. Why here? The timers keep counting their hold time even during an emergency. ME on the output line makes that irrelevant: whatever the timers do, no lock can be powered while ME is off. Step 10 shows what happens without it.

    Robustness habits

    • Put the overriding condition on the output line, where nothing can bypass it, not further up the chain.
    • Write each output in exactly one line. If you need another condition, add it to that line.
    Build

    Lines 18–20: the healthy flag and the display message

    Line 18 turns the emergency input into the flag that every other group uses. Lines 19 and 20 put a message on the module's display when the emergency circuit opens, and keep it there until someone resets it once the circuit is healthy again.

    Lines 18–20 · Emergency and message I9 → ME; text block X2
    1. L18 I9 drives [ ME. I9 is on while the circuit is healthy (step 2), so ME means SYSTEM HEALTHY.
    2. L19 Reset IA AND ME drives RX2, which removes the text. Reset does nothing while the emergency is still active.
    3. L20 mE (ME normally closed) drives TX2, which shows text block X2, "EMERGENCY STOP", as soon as ME drops.
    4. X2 stays on the display after the circuit is healthy again, until reset. The operator sees that something happened, even if nobody was there at the time.

    Text block X2

    In the text block editor, type EMERGENCY STOP on the display line. A text block can also show values such as a timer's time, but a fixed message is all this job needs.

    About "latching"

    Zelio auxiliary relays can be set to latching, meaning they keep their state through a power failure. ME is rewritten from I9 every cycle, so latching it gains nothing. Leave latching off unless a flag really must survive a power cut.

    Improve a delivered program: version 1 to version 2

    The program you have built is version 2. Version 1, as first delivered, used the same 27 lines with two differences: the healthy flag sat on the timer lines instead of the output lines, and the hold time was 10 s. It passed a normal-use test, because the doors interlocked correctly. The problem only shows up in an emergency.

    Version 1: ME on the timer lines
    Version 2: ME on the output lines

    What goes wrong in version 1

    Press the emergency button while D2 is open. ME drops and the timer triggers drop, but the timers are off-delays: they keep their contacts closed for the full hold time. With no ME on the output lines, locks D1 and D3 stay powered for another 10 s. Anyone trying to leave through those doors is held back exactly when they must not be.

    Engineer's thinking

    Why did version 1 look right?
    With ME on the timer lines, the emergency does reach the locks, eventually. A test that only checks "the locks release after an emergency" passes. The test must check when: immediately.
    Why not just shorten the timers?
    A shorter hold would shorten the delay but not remove it. Moving ME to the outputs removes the delay whatever the hold time is, and leaves the hold time free to be tuned for pressure recovery alone.
    What must be retested?
    Everything the change touches: every lock's hold time (new preset) and the emergency release with each door open (new output lines). Step 11 lists the tests.

    Robustness habits when you change someone else's program

    • Save the original before you touch it, and keep it next to the new version.
    • Change the program information (author, project name, version) so the printout shows which version is running.
    • Record what changed, where, why, and how you tested it, as in the table above.
    • Retest the old behaviour as well as the new one: the change must not break normal interlocking.

      Checklist and common mistakes

      A door interlock is small, but people depend on it. Check these points on every interlock you write or inherit.

      Common mistakeWhat it causesDo this instead
      The emergency condition on the timer lines, not the outputsLocks stay powered for the off-delay after an emergencyPut the healthy flag in series on every output line (step 8)
      A flag named after the bad state ("EMERGENCY STOPPED" for a flag that is on when healthy)The next engineer reads the logic upside downName flags after what on means: SYSTEM HEALTHY
      Door switch wired so that on = openA broken wire reads "closed", so the neighbours are never locked, and nobody noticesWire the switch to be on when the door is closed, and use the normally closed contact (i1) in line 1. A broken wire then reads "open" and locks the neighbours.
      Relying on the program alone for emergency releaseA program or module fault could keep a lock poweredAlso cut the lock supply with the emergency circuit in hardware
      A hold time chosen by guessToo long: people wait and prop doors open. Too short: the pressure does not recoverMeasure the pressure recovery of each room during commissioning
      Latching (retentive) set on flags that are rewritten every cycleNothing useful, and it misleads readersUse latching only for states that must survive a power cut
      Testing only that the locks releaseA delayed release passes the testMeasure the release time (step 11, tests 6 and 7)
      Changing a program without recording itNobody knows which version runs, or why it differsUpdate the program information and keep a change table (step 10)
