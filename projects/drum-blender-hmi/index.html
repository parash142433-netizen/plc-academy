Build an operator panel for a drum blender, step by step

In this tutorial you build the HMI for a pharmaceutical drum blender on a 9-inch SIMATIC Comfort panel, connected to an S7-1200. Each step states the problem, the design thinking, what you configure and the habits that keep a panel safe and easy to use. The last steps test the project, and a simulator runs the finished panel against a model of the machine.

Build steps
    Understand

    Start with the machine and the operator

    A drum blender mixes powders by turning a closed drum end over end at a set speed. The blend is good when the drum has made the right number of revolutions at the right speed. The PLC turns the drum. The panel's job is everything around it: who is blending, which batch, which recipe, whether the recipe makes sense, and a record that proves what happened.

    Engineer's thinking

    What decides a good blend?
    Speed and revolutions. Revolutions = RPM × minutes, so a recipe of 15 rpm for 14 minutes means 210 revolutions. The panel can check that the three numbers agree before a single gram is blended.
    What must the record show?
    Which machine, who, which product and batch, which recipe, when it started and finished, and how many revolutions the drum really made. In a regulated plant that record is evidence.
    What can hurt people?
    A turning drum. The guard door must stop it, and nobody may start it with the door open. Those interlocks live in the PLC; the panel shows them and never bypasses them.
    Who uses the panel?
    Operators run blends. An administrator manages recipes, users, the machine ID and the clock. Each gets only the buttons they need.

    Understand

    Choose the panel and set up the network

    The panel must show a full report on one screen, take string input for batch numbers, store recipes and log alarms. A 9-inch widescreen Comfort panel does all of that and leaves room for touch buttons big enough for gloved hands.

    The panel

    • SIMATIC TP900 Comfort: 9-inch widescreen touch, 800 × 480 pixels
    • PROFINET for the PLC connection
    • SD card slot for logs (\Storage Card SD) and USB for recipe files (\Storage Card USB)
    • Recipes, user administration, alarm logging and printing are all standard on Comfort panels

    The PLC and network

    • CPU 1214C DC/DC/DC runs the blender: drive, guard door, upright sensor, lock cylinder
    • PLC at xx.xx.xx.xx, panel at xx.xx.xx.xx, same subnet, mask 255.255.255.0
    • One HMI connection, named HMI_connection_2 in this project

    Set it up in TIA Portal

    1. Add the CPU 1214C and the TP900 Comfort to the project (Add new device).
    2. In Devices & networks, drag a line from the panel's PROFINET port to the CPU's. Give both an IP address in the same subnet.
    3. Switch to Connections and create the HMI connection between the two. TIA Portal names it; keep the name, the tags refer to it.
    4. In the panel's runtime settings, choose the start screen (step 3) and the language.

    Robustness habits

    • Write the IP plan down before you configure anything, and keep the panel and PLC on their own machine subnet.
    • Give the panel a fixed address. A panel that changes address loses its PLC.
    • Keep the PLC program and the HMI in one TIA project, so tag references stay valid when you change the data block.

    Engineer's thinking

    Why a fixed footer?
    The operator never has to remember how they got somewhere. Every main screen is one touch away, in the same place on every screen.
    Where do the reports go?
    They are not in the footer. The panel opens Blend Complete Report or Blend Failed Report by itself at the end of a blend (step 13), so a result can never be missed.
    What about "Drum Blender" and "Different jobs"?
    A title screen shown at start-up, and a small menu of jobs for future machine functions. Plan them now so the numbering and template stay consistent.

    Robustness habits

    • Structures with dot names (Target.RPM, Current.RPM) keep set and actual values side by side in every list.
    • Commands are written by the panel and reset by the PLC once handled, so a lost connection cannot leave a command stuck on.
    • Keep the data types of Recipe.* and Target.* identical. Loading a recipe is then a straight copy.
    Build

    Create the HMI tags

    With the PLC and panel in one project, you do not type addresses. Open the panel's tag table, add a tag, and pick the PLC tag from the data block. The HMI tag follows the PLC tag if it moves.

    1. In the panel, open HMI tags → Show all tags. Create a table per group, for example Blend, Job, Clock.
    2. For each tag, choose HMI_connection_2 and select the PLC tag from the data block. The data type comes with it.
    3. Set the acquisition mode to Cyclic in operation. Use 100 ms for values that move on screen (Current.RPM, Current.Revolution) and 1 s for the rest.
    4. Add internal tags (connection <Internal tag>) for values only the panel needs, such as the rows of the history table.
    TagAcquisitionWhy
    Current.RPM, Current.Revolution100 msThe operator watches them change
    Current.Remaining_Min, Remaining_Sec1 sChanges once a second anyway
    Alarm_Alarm1100 msShort alarms must not be missed
    Product_Name, Batch_No, Machine_ID1 sChange only on operator input

    Fast cycles cost communication

    Every tag on a visible screen is read at its cycle. Thirty tags at 100 ms load the connection far more than three. Use the fast cycle only where a person can see the difference.

    • Grey backgrounds and dark text for everything normal; colour only for states and alarms (ISA-101 style). Then a red indicator really stands out.

    • Highlight the button of the current screen, so the operator always knows where they are.

    Build

    Check the recipe before blending

    When the operator selects a record on Recipe Selection, the panel copies it to Target.* and checks it: speed and time inside the machine's limits, and revolutions equal to RPM × minutes. Only then does Recipe.OK go true and the start button come alive.

    VB script CheckRecipe called from the recipe list's selection event
    Sub CheckRecipe()
    Dim rpm, dur, rev, ok
    SmartTags("Numeric_analysis_done") = False     ' shows "Calculating Blend steps..."
    rpm = SmartTags("Target.RPM")
    dur = SmartTags("Target.Duration")
    rev = SmartTags("Target.Revolution")
    ok = (rpm >= 5) And (rpm <= 25) And (dur >= 1) And (dur <= 60)
    ok = ok And (Abs(rpm * dur - rev) <= 0.5)
    SmartTags("Recipe.OK") = ok
    SmartTags("Numeric_analysis_done") = True
End Sub
    1. Numeric_analysis_done drives the message: off = "Calculating Blend steps...", on with Recipe.OK = "Recipe blendable", on without = "Recipe not blendable. Please change recipe".
    2. Limits 5–25 rpm and 1–60 min are this machine's; take yours from the blender's manual.
    3. 0.5 tolerates rounding in a Real, but not a wrong number.
    4. The PLC checks Recipe.OK again before it starts. The panel's check is for the operator; the PLC's is for the machine.
    Try the checkPick a record or type your own numbers.

    The blending screen

    During a blend the operator wants three answers at a glance: is it running, how far is it, and how long is left. Put set and actual values side by side, and make the start conditions visible, so a refused start explains itself.

    ObjectConfiguration
    Set valuesOutput fields for Target.RPM, Target.Revolution, Target.Duration
    Actual valuesOutput fields for Current.RPM, Current.Revolution, Current.Elapsed_Min
    RemainingCurrent.Remaining_Min : Current.Remaining_Sec, calculated in the PLC from remaining revolutions ÷ RPM
    Start BlendingClick → SetBit "Start Blend"; enabled only when Recipe.OK is true
    Stop BlendingClick → SetBit "Stop Blend"; always enabled during a blend
    Status textText list on the PLC's state: Ready, Blending...., Blend Complete, Blend Failed

    Engineer's thinking

    Why does the PLC calculate the remaining time?
    It knows the real revolutions and speed. The panel only shows the result, so the number is the same on every screen and in every report.
    Why show the start conditions?
    "Start does nothing" is the most common call to maintenance. A list of conditions with a light for each answers it on the spot: door open, drum not upright, no job information.
    Can the panel stop the drum safely?
    The Stop button is a convenience. The real stop is the guard door and the emergency stop, wired to the drive. Never make a panel button the only way to stop a machine.

    Manual operation

    For loading, cleaning and maintenance the operator turns the drum by hand from the panel: jog it slowly, bring it upright, and lock it with the pneumatic lock cylinder. Manual commands work only in manual mode, and never during a blend.

    ButtonEvent and functionPLC interlock
    Auto / ManualClick → InvertBit "Auto Mode"Not during a blend
    Jog ModeClick → InvertBit "Jog Mode"Manual mode only
    Manual rotateSetBitWhilePressed "Manual rotate"Jog mode, door closed, lock cylinder up
    UprightClick → SetBit "Upright"Door closed; PLC creeps the drum to the upright sensor and stops
    Up Cylinder / Down CylinderClick → SetBitDown only with the drum upright and stopped

    Use SetBitWhilePressed for jogging

    With Press → SetBit and Release → ResetBit, a release that never arrives (a finger sliding off the button, a lost connection) leaves the drum turning. SetBitWhilePressed resets the bit when the press ends for any reason. The PLC should also stop jogging if the bit stops changing, or if the connection is lost.

    Alarms and the alarm log

    The PLC packs its alarm conditions into one word, Alarm_Alarm1. The panel turns each bit into a discrete alarm with a text, a class and a log entry.

    BitAlarm textClassCause
    0Door OpenErrors (acknowledge)Guard door switch open
    1VFD FaultErrors (acknowledge)Drive (VFD) fault contact
    2Cylinder not uprightErrors (acknowledge)Start or lock requested with the drum away from the upright sensor
    1. Under HMI alarms → Discrete alarms, add one alarm per bit: trigger tag Alarm_Alarm1, trigger bit, text and class.
    2. Place an alarm view on the Alarms screen and an alarm indicator in the template.
    3. Add a Reset button: Click → SetBit Reset_Alarm. The PLC clears its latches and resets the bit.
    4. Under Historical data → Alarm logs, create Alarm_log_1 on \Storage Card SD\Logs and assign the alarm class to it.

    Bit numbers in an S7 word are byte-swapped

    S7 stores a word high byte first. In a discrete alarm, trigger bit 0 is the lowest bit of the word, which lives in the second byte: DBX1.0, not DBX0.0. Bits 8–15 are in the first byte. Test every alarm once by forcing its bit, or you will find "Door Open" showing as "VFD Fault" on commissioning day.

    Robustness habits

    • Write alarm texts as the operator should read them: what is wrong, in three or four words.
    • Log to the SD card, not internal flash; the card survives a panel replacement.
    • Keep the PLC's alarm word for real alarms only. Status messages (blend complete) belong on screens, not in the alarm log.

    The history: a ten-place shift register

    When a blend ends, the PLC shifts Blend_History_Batch_ID[1..9] down to [2..10], writes the new batch into [1], and does the same for Blend_History_Recipe_no. Element 0 is the working place for the new entry. The history screen shows elements 1–10 in a table, newest first.

    Robustness habits

    • Freeze the report values in the PLC at the end of the blend. A report that reads live tags changes as soon as the next batch is entered.
    • Print or export the report before the operator leaves the screen; the Print Report button calls PrintReport.

    Users and access rights

    Two groups cover this machine: operators who blend, and administrators who look after recipes, users, the machine ID and the clock. Every button that changes something gets an authorization, so the panel greys it out for anyone not allowed.

    GroupAuthorizationsExample user
    Operator GroupOperate, Monitoroperator, password 1234
    Administrator groupOperate, Monitor, User administration, Recipe administrationadmin, password xxxx
    1. Under User administration, create the groups and the authorizations. Add a custom authorization Recipe administration.
    2. Assign authorizations to objects: Start/Stop and job fields need Operate; Settings, recipe view editing and user view need the administrator's.
    3. In the runtime settings, set an automatic logoff time, for example 5 minutes (0–60 allowed).
    4. On the event User change (scheduler), call GetUserName into username, so reports always carry the logged-on name.
    5. On the User administration screen, place a user view, so the administrator can add users and reset passwords in runtime.

    Example passwords are for the tutorial only

    Change every password before the machine goes into production, and give every person their own user. A shared "operator" login makes the report's operator name meaningless.

    Set the PLC clock from the panel

    Report times come from the PLC, so the PLC's clock must be right. The administrator sets it from Change Date Time; the PLC does the writing.

    TagTypeUse
    current_SYS_DateTimeDTLPLC system time, read cyclically with RD_SYS_T
    current_LOC_DateTimeDTLPLC local time with RD_LOC_T, shown on the panel
    set_current_SYS_DateTimeDTLNew time typed by the administrator
    SYS_DateTime_input_finishedBoolSet by the Set button; the PLC calls WR_SYS_T with the new time, then resets it

    Engineer's thinking

    Why not set the panel's clock instead?
    The timestamps that matter (blend start and finish) are taken in the PLC. Set the PLC, then let the panel follow it with the Date/time PLC area pointer, so both always agree.
    System time or local time?
    The S7-1200 keeps system time (UTC) and works out local time from its time-zone setting. Write system time, display local time.

    Back up the panel

    In TIA Portal, select the panel and use Online → HMI device maintenance → Backup (or SIMATIC ProSave). The result is a .brf file holding the panel's operating system, the compiled project, the recipes, the user administration and the network settings. With it, a replacement panel is running again in minutes. Keep one after commissioning and one after every change.

    A backup is not the source

    The .brf restores a panel, but you cannot open it in TIA Portal to change a screen. Archive the TIA project as well, with the same date and version, every time you make a backup.
