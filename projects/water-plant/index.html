Siemens S7-200 · CPU 226 · STEP 7-Micro/WIN 4.0

Building the Water Plant PLC program from scratch

A step-by-step reconstruction of how an automation engineer would design and write this real project. It is based on the project file Water Plant.mwp and its program listing PLC.awl. Each step explains the problem, the thinking, the code that solved it and how to make it robust. It ends with a live simulator of the finished program.

Build steps
    Understand

    Start with the process, not the PLC

    Good PLC programs are designed away from the keyboard. Before writing a single network, the engineer has to understand the plant: what it makes, in what order things must happen, what can be damaged, and what the operator needs to do.

    Engineer's thinking

    What must run, and in what order?
    Tank, then pump 1 and stage 1, then pump 2 and stage 2, then polishing. Each stage only starts when the one before it is delivering.
    What can be damaged?
    Pumps running dry (no tank level), membranes over-pressurised, polishing modules powered without water flowing through them.
    What protects the product?
    Quality checks (conductivity, rejection, temperature) decide whether water goes to the users.
    What does the operator need?
    Start and stop, hand control for maintenance, a cleaning cycle, alarm acknowledgement, and setpoints they can adjust.
    Who else needs data?
    A touch panel (HMI) on the skid and a supervisory system (SCADA or BMS) on the network.

    Requirements to build against

    IDRequirementBuilt in step
    R1Start and stop from the HMI, only when the plant is safe to start7
    R2Never run the pumps without water in the break tank; keep the tank topped up7
    R3Start in a safe order, with a low-pressure flush before full production8
    R4Let maintenance staff run any output by hand, without upsetting the plant9, 10
    R5Hold pressure and flow automatically with variable-speed pumps11

    What the project file tells us

    The .mwp file is a compressed STEP 7-Micro/WIN project. Unpacked, it holds more than the program listing: the data block with every commissioning value, the wizard configurations, and timestamps that show how the project grew.

    Evidence from the files

    • Saved with STEP 7-Micro/WIN 4.0.9.25 (V4.0 SP9) for a CPU 226 with firmware 02.01. Project name "Water Plant"; data page "Version" stores 1.2.
    • One main block, 14 subroutines and one interrupt. Six blocks were generated by wizards or supplied locked (password-protected).
    • The user symbol table is empty and every network comment is the default text. The original programmer worked with absolute addresses and left no comments. This reconstruction adds the explanation that was never written down.
    • The data block is organised in pages: Data Block (60 values), ANOL_RANGE (48 scaling limits), COMM (7 commissioning setpoints), Version, plus pages the PID and Ethernet wizards created.
    Understand

    List the I/O and choose the hardware

    Count every signal before choosing a controller. The I/O list becomes the contract between the electrical design and the program, and it decides the CPU and modules.

    The count

    • 15 digital inputs: permissives, drive healthy signals, running feedbacks
    • 16 digital outputs: pumps, valves, polishing modules, horn, lamps
    • 24 analog inputs: conductivity, temperature, pressure, flow, level, voltage, current
    • 2 analog outputs: pump speed references to the drives

    The hardware chosen

    • CPU 226: 24 DI / 16 DO onboard, enough for all digital I/O with no expansion
    • 6 analog modules, 4 channels each: AIW0–AIW46
    • 2 analog outputs as 4–20 mA (the PID wizard scales them 6400–32000)
    • CP 243-1 Ethernet module in slot 6 for SCADA
    • Windows CE touch panel for the operator

    Watch the expansion limit

    A CPU 226 accepts at most seven expansion modules. This design uses all seven (six analog plus the CP 243-1). Any future signal needs a different solution, so leave spare capacity when you can.

    Fail-safe signal design

    Look at how the digital inputs are used: the program alarms when I1.2, I1.3, I1.4 and I1.5 go off. These are "healthy" signals wired normally closed. A broken wire, a blown fuse or a pulled connector then looks exactly like a fault, so the plant stops instead of carrying on blind.

    Plan

    Plan the memory map before writing code

    An S7-200 has one big V memory area that the program, the HMI, the SCADA link and the wizards all share. Decide up front which address ranges belong to what. Otherwise two features will one day write the same byte.

    V memory map of the Water PlantClick a block to see what lives there

      Engineer's thinking

      Group by owner and purpose
      Commands and sequence bits low (VB0–VB14), scaled values together (VD100–VD144), setpoints together (VD350–VD396), alarm limits together (VD900–VD1022). The HMI designer then maps whole blocks, not scattered tags.
      Make alarms contiguous
      All alarm bits sit in VB150–VB159. One block move (BMD VD150, VD1148, 5) sends every alarm to SCADA, and comparing those bytes with a snapshot detects new alarms for the horn.
      Reserve space for the wizards
      The PID wizard needs an 80-byte loop table. It was given VB228–VB307 and VB638–VB717, wedged between other areas with no spare bytes.
      Store every default in the data block
      Timers, setpoints, ranges and limits all have starting values in data block pages. A new CPU or a memory reset then starts with sensible values, not zeros.

      Gaps the data block can't fill

      Three values in the data block are never used by the program: VW44 = 1200, VD46 = 150.0 and VD52 = 60.0. They are probably left over from an earlier version or meant for the HMI. Unused memory with values in it confuses the next engineer, so document it or remove it.

      Plan

      Design the program structure

      Split the program by the question each part answers. The key idea in this project is layering. Auto, Manual and Sanitise only produce requests in V memory; one routine, Run, decides what the physical outputs actually do.

      BlockThe question it answersWhy it is a separate block
      OB1What runs every scan, and in what order?Keeps the main block a short, readable schedule plus a few global functions
      SBR4 + SBR3/9What are the measurements in real units?One routine, called 24 times with parameters, instead of 24 copies of the same maths
      SBR0 AutoWhat would the plant do by itself?Sequence logic stays free of manual and safety details, so it reads like the process
      SBR1 ManualWhat has the operator asked for in hand?Hand logic for 12 outputs in one place, all built on one pattern
      SBR5 SanitiseWhat does the cleaning cycle need?A batch sequence with its own timers that must never mix with production logic
      SBR2 RunShould this output be on right now?Each output is written once, so interlocks cannot be bypassed by any mode
      SBR7 AlarmsIs anything wrong, and how bad?One home for detection, delays, latching and the shutdown decision
      SBR11 NetworkWho else needs the data?Communication changes (added in 2013) touched only this block

      Scan order matters

      OB1 calls Auto → Manual → Run → Analogue → Sanitise → Alarms → Network. So Run decides with analog values from the previous scan, and alarm interlocks act one scan late. At scan times of a few milliseconds this is harmless. In a new design, use Inputs → Alarms → Requests → Outputs → Comms, so every decision in a scan uses the same fresh data.

      Robustness habits

      • Give field devices time to boot before trusting them (here 45 s), and mask alarms that would only be noise during that time.
      • Build lamp flashing from timers inside the program, so the rhythm doesn't depend on the scan time.
      • Configuration options belong in clearly named bits set in one place, never scattered constants.
      • Always publish a heartbeat. An HMI showing frozen values is worse than one showing "PLC not responding".

      Robustness habits

      • Write reusable maths once, with parameters, and test it once: 4 mA, 12 mA and 20 mA, plus a non-zero Low limit.
      • Keep ranges in data, not code.
      • Detect under-range (below about 3.6 mA) as a fault. Never let a dead transmitter look like a real low reading.
      • Decide what a failed signal should do to the process. Step 16 shows what this plant does when its level transmitter fails.

      Robustness habits

      • Separate "selected" (operator intent) from "running" (process allows it). A paused plant restarts by itself, a stopped one does not.

      Engineer's thinking

      Why timers in a chain, not a step counter?
      Each step's timer has the previous step as its input. If anything upstream drops, every later step drops in the same scan, so shutdown is automatic and needs no extra code. The price is less visibility: there is no single "step number" to show on the HMI.
      Why keep presets in V memory?
      TON T103, VW38 reads its preset from VW38, which the operator can tune on the HMI without a program download.

      Watch this sequence live in step 16: press Start in the simulator and follow the timers.

      Robustness habits

      • Hand mode is still subject to safety interlocks. Only the sequence is bypassed, never the protection.
      • Clear hand selections on an emergency stop.
      • Use the same pattern for every output, so one review covers all twelve.
      • Six outputs (Q1.1–Q1.6) have no interlock in hand at all. Review that in a risk assessment.

      The design rule

      Write every output in exactly one network. With one place per output, an interlock added there protects the output in every mode, and anyone investigating "why is this pump off?" has only one network to read.

      Auto-restart after a drive fault

      If I1.4 drops, pump 1 stops at once. But Auto stays selected and V2.0 stays on, so the pump restarts by itself the moment the healthy signal returns. Some plants want exactly that; many want an operator restart after a drive trip. Decide deliberately (try "Pump 1 drive fault" in the simulator).

      4. N21 Tuning values are copied from HMI registers into the loop table every scan (VD70 → gain at VD240). The operator tunes without opening the wizard.
      5. N39 The wizard's setpoint range was set for AIW14 (0–10). The flush setpoint is rescaled so the same percentage is meant: 5.0 × 10 / 25 = 2.0.

      Robustness habits

      • Use the wizard for the algorithm, but keep the operator interface (setpoints, tuning, auto/manual) in your own V memory.
      • Force the controller output to a known value whenever the actuator is off.
      • When switching measurements, convert setpoints so the same physical meaning is kept.
      • The wizard also stored autotune parameters (deviation 0.08, hysteresis 0.02, initial step 0.1, 7200 s watchdog), so the PID Tune Control Panel was available at commissioning.

      Engineer's thinking: why not just use timers?

      An S7-200 100 ms timer counts to 32767, which is 3276.7 s or about 54 minutes. Stage 2 lasts 90 minutes and stage 3 six hours. Neither fits in one timer. A DINT counted down once per second fits easily, and the HMI can show the remaining time directly from VD204, VD212 and VD224.

      Points to decide

      • Once complete, V12.2 blocks a new cycle until someone presses Stop/reset. That may be intended as an acknowledgement, but it must be explained to operators.
      • If a trip or loss of I1.2 aborts the cycle, the finished stages stay flagged and a restart skips them. Only Stop/reset clears them.
      • The cycle is purely time-based. Nothing checks temperature or chemical strength, so the cleaning effect must be proven another way.

      The horn: noticing new alarms

      The horn should sound for a new alarm, not keep sounding for old ones. Networks 83–87 compare each live alarm byte (VB150–VB159) with a snapshot (VB160–VB169). A rising difference sets V14.0, which latches the horn. After 3 s (T121) the snapshot is updated; when every alarm has cleared, it is zeroed.

      Robustness habits

      • Every alarm needs an enable. An alarm that fires every time the plant starts teaches operators to ignore alarms.
      • Separate warnings from trips, and keep the trip list in one network so it can be reviewed in one glance.
      • Latch alarms so a short event is never missed, and only allow a reset once the condition has cleared.
      • Detect new alarms bit by bit. A byte "greater than" compare can miss one when another bit in the same byte clears in the same scan.

      Robustness habits

      • Put everything that leaves the PLC in one exchange area (here VB1124–VB1180). The SCADA engineer gets one contiguous range.
      • Give each consumer a heartbeat and make it alarm when the heartbeat stops.
      • Keep a single time master and synchronise the others from it.
      • Check your reset logic: SBR11 N6 resets the heartbeat when VW3898 exceeds 9999. That should be VW1178 (finding F2).

      Test, commission and review

      A program is only robust once it has been proven. This is the order a careful engineer follows, then what a fresh review of this project found.

      1. Desk check. Read every network against the requirements list from step 1. Compile, and clear every warning.
      2. Simulate. Force inputs with the PLC on the bench and watch the status chart: start sequence, every interlock, every alarm.
      3. I/O check on site. Prove each wire: every input from the field device, every output to its actuator, each analog at 4, 12 and 20 mA.
      4. Loop check and tuning. Run each PID in manual, then auto. Use the PID Tune Control Panel and record the final values in the data block. This project keeps them on a page named COMM.
      5. Sequence and alarm challenge. Run the start sequence and the sanitise cycle with real water. Trigger every trip on purpose.
      6. Archive. Upload the final program and data block, save the project with a version number (here VD500 = 1.2), and store a backup off the machine.

      What a fresh review found

      None of these stop the plant working day to day, which is why they survived. They are good examples of what testing should catch.

      Level transmitter failure, a worked example

      If AIW22 loses its signal, the scaling routine reports −25 %. In the same scan, V2.5 sets (fill demand) and V2.4 resets (pumps stop). For 5 s, until the signal-failure trip latches, the fill valve opens on a tank whose level is unknown. Once the trip drops Auto, the valve closes. A safer design treats a failed level signal as "high" for filling purposes. Try it in the simulator.
